# Modules

## Module boundary rules

Each module owns its domain model, application services, persistence repositories, API controllers, and events. It may expose only documented interfaces/events. Direct reads or writes to another module's tables are prohibited; compose cross-module read models through query services or projections. Provider-specific SDKs and transport types are isolated in integration adapters and must not leak into business-domain modules.

## API Layer

All external traffic enters through the API Layer before it reaches an individual module. This includes browser/API requests, Socket.IO connection and subscription requests, provider webhooks, and approved partner/API-client calls. The layer performs transport-level concerns consistently: request correlation, authentication, tenant resolution, authorization, input/schema validation, rate limiting, security headers, audit/logging context, error normalization, and request-size controls.

After those checks, the API Layer delegates to a module's application use case; it does not contain domain business rules or bypass module authorization policies. Webhooks use provider-specific signature/challenge verification before durable inbox persistence. Socket.IO connections use the same identity and policy rules as REST, and room membership is authorized server-side.

## Ownership and coupling

The Inbox owns message/conversation state; Contacts owns identity and consent; Campaigns owns campaign execution but delegates actual delivery to the WhatsApp Provider application interface. Tenant Management owns tenant configuration and entitlements, while the WhatsApp Provider module owns WhatsApp-specific provider/channel behavior.

The Integration Layer is a generalized technical boundary, not a business-data owner. It provides isolated adapters for CRM, Meta/WhatsApp, AI, Email, Calendar, Payment, and future providers. Domain modules depend only on provider-neutral ports exposed by their owning capability module or the Integration Layer—not on another provider SDK or credential store. CRM Integration owns CRM mappings and synchronization state, never CRM data as an authoritative replacement. Analytics is projection-only and must not become a write dependency for operational workflows.

**AI boundary rule:** the Inbox module never calls an AI provider or AI adapter directly. It requests approved capabilities only through the AI Assistance module's provider-neutral application interface. AI Assistance applies tenant policy, authorization, data minimization, safety controls, audit/usage tracking, and provider selection before returning a normalized result. This same rule applies to every other business module.

## Future extraction seams

Likely first candidates for independent deployment are the WhatsApp Provider, Campaigns/dispatch, Integration Layer/CRM Integration, AI Assistance, and Analytics. Extraction requires replacing in-process event handlers with a broker while preserving the event schemas, idempotency contracts, and module APIs defined here.
